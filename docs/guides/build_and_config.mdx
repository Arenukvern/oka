# Build & configuration guide

How to run, build, and extend oka. Why-rationale lives in the
[design FAQ](design_faq); settled decisions in
[`docs/decisions/`](../decisions/index); stores and accounts in the
[accounts & stores guide](accounts_and_stores).

## 🏠 Setup Hub

**Q: How do I install oka and its Android SDK?**
```bash
dart pub global activate oka    # from the repo: just install && just global
oka get android-sdk             # bootstrap SDK into ~/.oka/android-sdk
oka doctor                      # verify everything
```

**Q: How do I start a new project (oka init)?**
```bash
oka init               # full-Dart config: scaffolds tool/oka_pipeline.dart
                       # (typed AndroidBuild/FlutterBuild) — no oka.yaml
oka init --yaml        # legacy YAML-first scaffold (prints a Gradle
                       # conversion checklist when android/app/build.gradle
                       # exists — ADR-0012: no embedded LLM)
oka init --from-yaml   # converts an existing oka.yaml 1:1 into the typed
                       # Dart entrypoint (ADR-0010)
```
`oka build` discovers `tool/oka_pipeline.dart` by convention. Non-interactive
sessions (CI/agents) skip overwrite prompts; pass `--force` to overwrite.
Migrating an existing Gradle app: the
[Gradle migration guide](gradle_migration).

**Q: Where does configuration live?**
Three sources, merged in precedence order (later wins):
1. `oka.yaml` or a top-level `oka:` section in `pubspec.yaml`,
2. typed Dart config in `tool/oka_pipeline.dart` (ADR-0010 — deep-merges
   over the YAML baseline),
3. CLI flags (`--release/--aab/--abi/--target/--dart-define`).

**Q: How do I depend on oka packages before their first pub.dev release?**
`oka_android` declares a hosted `oka_core` constraint, so until both are
published, host projects resolve them locally:
```yaml
dependency_overrides:
  oka_android:
    path: /path/to/oka/packages/oka_android
  oka_core:
    path: /path/to/oka/packages/oka_core
```
Publish order (release train): `oka_core` → `oka_android` → `oka`. Drop the
overrides once published.

**Q: How do I catch dependency/version resolution problems before building?**
```bash
oka explain --deps            # resolve the plugin dependency plan against
                              # the local ~/.oka maven cache (offline-safe)
oka explain --deps --network  # full resolution incl. downloads + POM
                              # transitives; exit 1 on hard failures
```
The plan composes the same collector and resolver the build uses, so plan
and packaging cannot disagree. Cache-only misses print
`⚠️ not in local maven cache`; with `--network` a resolution failure prints
`❌` and fails the dry-run. See
[ADR-0008](../decisions/0008-dependency-plan-dry-run).

**Q: How do I build the example app?**
```bash
cd example && flutter pub get && oka build apk
# output: .oka_cache/build/debug/app-debug.apk
```

## 🔨 Builds

**Q: How do I build a release APK?**
```bash
oka build apk --release
# output: .oka_cache/build/release/app-release.apk
```
Release AOT-compiles Dart to native `libapp.so`, applies R8 shrinking, and
signs with the release keystore (see [Signing](#-signing--versioning-g2)).
Incremental caches are shared per-step and keyed by mode.

**Q: How do I build an App Bundle (AAB) for Play Store?**
```bash
oka build aab            # or: oka build release aab
# output: .oka_cache/build/<mode>/aab/app-<mode>.aab
```
Same config, plugins, extra deps, icons and deeplinks as APK builds.
An .aab is an upload format — verify it locally with bundletool:
```bash
oka get bundletool          # one-time download into ~/.oka/tools
oka build aab --verify-aab  # bundletool build-apks --mode=universal
adb install -r .oka_cache/build/<mode>/aab/universal/app-universal.apk
```
For the release gate, run the project-declared release target
(`oka run release-google`) — its verifier runs `bundletool validate`, can
generate a device spec from a connected device, builds the matching split
APK set, and reports independent gates (sha256, ABIs, split APKs). An
unavailable verifier is recorded as failed/unverified, never as silent
compatibility.

**Q: How do multi-store targets fit into the build?**
Stores are project-declared targets, not build switches — `oka build` stays
store-neutral. Declare targets in `tool/oka_pipeline.dart`, inspect with
`oka explain --targets`, run one with `oka run <declared-name>`. Per-store
variants, accounts, and the GMS-free Huawei build:
[accounts & stores guide](accounts_and_stores).

**Q: How does R8 shrinking work?**
Release builds run the **real R8 shrinker** over the full program closure
(app + Flutter embedding + plugin jars). R8 ships via Google Maven, so oka
provisions it into `~/.oka/tools/r8` (`oka get r8`, or self-heal;
`OKA_NO_AUTO_INSTALL=1` opts out). Outputs land under `<buildDir>/r8/`:
`mapping.txt` (upload with your Play release) and `configuration.txt`. A
release build fails hard if R8 is missing or produces no mapping. Default
keep rules cover the reflection surface real apps rely on; project rules are
typed config:
```dart
AndroidBuild(
  // default: release shrinks. Set false only deliberately:
  // enableOptimization: false,   // keeps R8 + mapping, disables shaking
  proguardFiles: ['android/proguard-rules.pro'],  // merged with defaults
)
```
A missing rule file fails the build.

**Q: How do I install & launch on a device?**
```bash
oka run device                  # install → launch → failure-signature scan
# manually:
adb install -r example/.oka_cache/build/debug/app-debug.apk
adb shell am start -n com.example.example/.MainActivity
adb logcat -d -b crash | grep com.example
```

**Q: How do I run tests?**
```bash
just test    # dart test
just lint    # dart analyze
```

## 🎛️ Full-Dart project config (ADR-0010)

**Q: Can I drop oka.yaml and configure everything in Dart?**
Yes. `tool/oka_pipeline.dart` is the whole config, strictly typed:

```dart
// tool/oka_pipeline.dart
Future<void> main(List<String> args) => okaRun(
  args,
  oka: const Oka(
    pipelines: [
      AndroidPipeline(
        config: AndroidBuild(          // was android: + top-level name:
          name: 'example',
          packageName: 'com.example.example',
          minSdk: '23', targetSdk: '36', compileSdk: '36',
          versionCode: 51, versionName: '3.22.0',
          abis: ['arm64-v8a'],
          javaVersion: 17,
          kotlinCompilerArgs: ['-opt-in=kotlin.ExperimentalStdlibApi'],
        ),
        flutterConfig: FlutterBuild(   // was flutter:
          entrypoint: 'lib/main_prod.dart',
          treeShakeIcons: true,
        ),
        overrides: PipelineOverrides(  // was pipeline: + android.icon/manifest
          resourceConfigs: ['en', 'ru'],
          manifest: ManifestSpec(permissions: [...]),
        ),
        steps: [...AndroidPipeline.defaultSteps],
      ),
    ],
  ),
);
```

- Field mapping: `android:` → `AndroidBuild`, `flutter:` → `FlutterBuild`,
  `pipeline:` + `android.icon/manifest/res_dirs` → `PipelineOverrides`,
  top-level `name:` → `AndroidBuild.name`.
- Kotlin compiler requirements are declarative
  (`AndroidBuild.kotlinCompilerArgs`); `kotlinSources` stays a list of
  source paths.
- **Migrating**: `oka init --from-yaml` → `oka explain` →
  `oka build apk && oka compare old.apk .oka_cache/build/debug/app-debug.apk`.
  Proven byte-equivalent (ADR-0010 evidence). Full working file:
  [example/tool/oka_pipeline.dart](https://github.com/Arenukvern/oka/blob/main/example/tool/oka_pipeline.dart).

**Q: How do I customize the pipeline without editing oka?**
The composition root is a Dart program: add `BuildStep`s, compose step
lists, branch on args (per-brand pipelines —
[accounts & stores guide](accounts_and_stores)). `okaRun` handles arg
parsing, `oka.yaml` merge, SDK/cache dirs. Steps declare `requires`/
`provides` artifact sets; the runner **validates the whole chain before any
tool runs** and fails naming the missing producer. Reusable logic ships as
ordinary Dart packages — depend on `oka_android` (light deps) in the host
app, not the `oka` CLI.

```dart
class MyStep implements BuildStep {
  @override
  String get name => 'my-step';
  @override
  Future<StepResult> run(BuildContext ctx, PipelineState state) async {
    // read config from ctx, share artifacts via state
    return StepResult.success();
  }
}
```

Data flows between steps via `PipelineState` — a typed blackboard
(`state.abis`, `state.flutterAssetsDir`, `state.dexFiles`, `state.apkPath`,
…); custom keys use the `[]` operator.

**Q: How do I customize the Android manifest?**
The manifest is a typed `ManifestSpec` rendered by `host-codegen` — no XML
patching:
```yaml
android:
  manifest:
    permissions: [android.permission.INTERNET, android.permission.CAMERA]
    cleartext_traffic: true
    flutter_deeplinking: true
    application_attributes: {android:icon: "@mipmap/ic_launcher"}
    activity_attributes: {android:theme: "@style/LaunchTheme"}
    application_meta_data:
      - name: io.flutter.embedding.android.NormalTheme
        resource: "@style/NormalTheme"
    deeplinks:
      - {scheme: https, host: example.com}   # autoVerify
      - {scheme: myapp}                       # scheme-only custom scheme
```
Hooks override it wholesale via `ManifestSpec.copyWith`. The user `res/`
tree (themes, splash, mipmaps) merges via `android.res_dirs`.

## 🔁 Dev Loop Station (ADR-0011)

Three device-flow surfaces, one story — `oka launch` is an alias of
`oka run device`, and `oka dev android` reuses the same device steps plus
the VM-service session steps, through the same validated pipeline
machinery. (The bare `oka dev` is the converged desktop/web session —
[ADR-0037 §6c](../decisions/0037-air-channel-invisible-patches).)
History and phase evidence: [hot_reload_plan](hot_reload_plan).

```bash
oka build apk --debug          # 1. oka owns assemble → package → sign;
                               #    records run_session.json (flag parity)
oka run device                 # 2. one-shot: install + launch + failure-
                               #    signature scan. No session.
oka dev android                # 3. parity check → install → launch → logscan
                               #    → VM service attach → hot reload/restart
```

`oka dev android` controls:

- **Human TTY**: `r` hot reload · `R` hot restart (**loses app state**) ·
  `q` quit (stops the app) · `d` detach (app keeps running). Oka renders all
  progress — never the flutter TUI.
- **Agent (`--json`)**: structured events on stdout
  (`{"scope":"dev","event":"session.ready"…}`); control lines on stdin:
  `reload` / `restart` / `stop` / `detach` / `quit` (wait for
  `session.ready` before sending).
- **Agent (`--watch`)**: non-TTY watcher. Dart-only changes reload
  automatically; native/res/manifest/asset/config changes print the honest
  full-rebuild command (hot reload is Dart-only — never a dex push,
  ADR-0011 §5). `--watch --rebuild-on-native` runs it automatically.

Flag parity is enforced: `oka dev android` validates the requested target/defines
against the recorded `run_session.json` and refuses mismatches naming the
differing fields; the session flutter binary always comes from the recorded
SDK path, never `PATH`. Profile/release refuse loudly — debug (JIT) only.
Readiness: `oka doctor` (manifest, recorded-SDK binary, device ready).

## ⚡ Incremental build cache

Each step stores its input fingerprint *and per-input digests*;
`oka why <step>` (e.g. `oka why release-aot`) names which input changed.
`plugin-packaging`, `flutter-assemble`, `release-aot` and `compile-and-dex`
are fingerprint-gated — unchanged inputs skip Maven resolution, kotlinc and
d8 entirely; production-app repeat builds drop to ~25s. Fingerprints live in
`.oka_cache/build/<mode>/step_cache.json`; `oka clean` resets.

**Q: How do I re-run a single pipeline step against the existing cache?**
```bash
oka debug step compile-and-dex              # one step (+ upstream prefix,
                                            # cache-hit cheap), verbose
oka debug step --list                       # discover available steps
oka debug step plugin-packaging --project /path/to/app
```
Same context building as `okaRun` — the probe sees exactly what a build
sees. Disk usage and scoped cleanup:
[cache storage and cleanup](cache_storage).

## 🔐 Signing & versioning (G2)

```yaml
android:
  version_code: 51          # injected via aapt2 --version-code
  version_name: 3.22.0      # injected via aapt2 --version-name
  resource_configs: [en, ru]  # aapt2 -c qualifier filter
  exclude_plugins: [integration_test]  # test-only plugins
  signing:
    keystore: keys/release.jks
    alias: upload
    store_password_env: OKA_STORE_PASS   # secrets via env, never yaml
    key_password_env: OKA_KEY_PASS
```

Signing fallback chain: explicit config → `oka.yaml android.signing` →
`android/key.properties` (Gradle-compatible: `storeFile`, `keyAlias`,
`storePassword`, `keyPassword`) → debug keystore (dev only; release builds
warn loudly — stores reject debug-signed artifacts). Per-brand keystores and
stable-identity rules: [accounts & stores guide](accounts_and_stores).

## 🔧 Build Pipeline Station (ADR 0002)

Default order (composed in `lib/src/pipeline/default_pipeline.dart`):

| # | Step | File |
|---|------|------|
| 1 | `ensure-android-sdk` | `steps/host_steps.dart` |
| 2 | `resolve-abis` | `steps/host_steps.dart` |
| 3 | `plugin-packaging` | `steps/host_steps.dart` |
| 4 | `host-codegen` (manifest, MainActivity, icon) | `steps/host_steps.dart` |
| 5 | `flutter-assemble` | `steps/flutter_steps.dart` |
| 6 | `engine-extraction` | `steps/flutter_steps.dart` |
| 7 | `release-aot` | `steps/flutter_steps.dart` |
| 8 | `dependency-resolve` | `steps/flutter_steps.dart` |
| 9 | `extra-deps` | `default_pipeline.dart` |
| 10 | `compile-and-dex` | `steps/tool_steps.dart` |
| 11 | `extra-assets` | `steps/asset_steps.dart` |
| 12 | `package-and-sign` | `steps/tool_steps.dart` |
| 13 | `validate-layout` | `steps/tool_steps.dart` |

Shared tool logic (aapt2/javac/d8/zipalign/apksigner invocations) lives in
`lib/src/pipeline/toolchain.dart`. Config precedence: built-in defaults <
`oka.yaml` `pipeline:` section < Dart composition (a user-built `Pipeline`
always wins).

## 📦 Dependencies Station

**Q: How do I add an extra runtime dependency without editing oka?**
In the project's `oka.yaml`:
```yaml
pipeline:
  extra_deps:
    - "com.squareup.okhttp3:okhttp:4.12.0"
```
Resolves from Google Maven / Maven Central into the shared store's `maven/`
directory, follows the same limited-depth POM transitive closure as plugin
dependencies (ADR-0008), and is dexed into the APK. AAR dependencies also
package their `jni/` natives — filtered to the build's ABIs — and `res/`
trees, so host Kotlin/Java compiled against an extra dep both links and
runs.

**Q: A build fails with `NoClassDefFoundError: Lfoo/Bar;` — what now?**
Oka auto-suggests the Maven artifact on build failure. To resolve manually:
```bash
oka get dep androidx.window:window:1.3.0
```
This caches the artifact and prints the exact `oka.yaml` snippet. Mapping
table: `lib/src/build/dependency_suggest.dart` (`kKnownClassArtifacts`) —
add new entries there when you discover gaps. A `NoClassDefFoundError` in a
plugin class followed by ALL plugins failing to register usually means a
dependency that only Gradle module metadata declares (`.module`, not the
POM) — e.g. `androidx.camera` needs `kotlinx-atomicfu`; oka parses `.module`
runtime deps (`parseModuleRuntimeDependencies` in `lib/src/maven_resolver.dart`).

**Q: Where is the default AndroidX embedding dependency set?**
`flutterEmbeddingAndroidXDeps()` in `lib/src/build/dependency_cache.dart`.
Edit only when adding artifacts needed by *every* Flutter host;
project-specific ones belong in `pipeline.extra_deps`.

## 🎨 Assets & Icon Station

**Q: How do I bundle extra assets beyond pubspec?**
```yaml
pipeline:
  extra_assets:
    - from: build/generated-config.json   # file or dir, project-relative
      to: generated-config.json           # flutter_assets-relative destination
```
Runs after flutter-assemble; sources must exist or the build fails.

**Q: How do I package a local .aar file?**
```yaml
pipeline:
  local_aars:
    - libs/my-native-lib.aar   # project-relative path
```
Oka extracts classes.jar (dex input), `jni/<abi>/*.so` natives (staged to
`lib/<abi>/`), and `res/**` XML (merged into aapt2 compile). Resource-only
AARs (no classes.jar) are supported. The same extraction happens
automatically for Maven AARs (`extractAarPayload` in
`lib/src/build/dependency_cache.dart`).

**Q: How do I set the launcher icon?**
```yaml
android:
  icon:
    background_color: "#E8F5E9"         # or @color/ref
    vector: assets/icon/foreground.xml  # VectorDrawable XML (108dp viewport)
    monochrome: assets/icon/mono.xml    # optional, Android 13+ themed icons
    name: my_launcher                   # optional, base resource name
    manifest_ref: "@mipmap/my_launcher" # optional, full override — generate nothing
```
Vector-first: no PNG tooling; works on API 26+. Generated resources use
`name` (default `ic_launcher`). Two user-owned paths: ship your own icons
via `pipeline.res_dirs` (oka skips generation when the merged res tree
already defines the icon), or set `manifest_ref` to opt out entirely.
Implementation: `lib/src/build/launcher_icon.dart`.

**Q: How do I add deeplinks?**
```yaml
pipeline:
  deeplinks:
    - scheme: https
      host: oka.example.com
      pathPrefix: /app
```
Generates `autoVerify` intent-filters on MainActivity. Test with:
```bash
adb shell am start -a android.intent.action.VIEW \
  -d "https://oka.example.com/app/settings" com.example.example
```

## 🩺 Troubleshooting Station

**Q: Install fails with `-124: resources.arsc ... uncompressed and aligned`?**
The packager must store `resources.arsc` uncompressed (`zipStagingToApk` in
`lib/src/build/apk_layout.dart`) and zipalign with `-p 4`. Both are wired;
if regressed, device installs on Android 11+ fail.

**Q: App crashes at launch with missing classes but tests pass?**
Runtime link errors don't surface at compile time. Reproduce with adb, read
`adb logcat -d -b crash`, then follow the dependency-recovery flow above.

**Q: Device shows `unauthorized` in adb?**
Accept the USB debugging dialog on the phone (unlock first). If stale:
Developer options → Revoke USB debugging authorizations → replug.

**Q: kotlinc fails with JDK version errors?**
Kotlin 2.1 rejects JDK 25+; `kotlinJavaEnvironment()` in
`lib/src/pipeline/toolchain.dart` probes for JDK 17–21 automatically.

## 🪜 Verification Station (ADR-0029)

**Q: How do I prove a release build actually starts?**
```bash
oka run verify
```
Walks the ladder: artifact provenance → snapshot↔engine pairing → install →
device health → launch → process alive → Dart `main()` (startup beacon) →
first rendered frame → failure signatures. Each rung prints a typed verdict;
the run fails at the first broken rung with the cause and fix. Compose it in
`tool/oka_pipeline.dart` (`VerifyTarget(...)`); add rungs and project failure
signatures as values — see
[ADR-0029](../decisions/0029-build-provenance-and-verification-ladder).

**Q: What is `oka-provenance.json` inside my APK?**
The build's birth certificate (ADR-0029 D1): engine variant and
`libflutter.so` hashes, AOT snapshot hash + build id, pub-resolution hashes,
assemble fingerprint, mode and ABIs. Read it without oka:
`unzip -p app.apk assets/flutter_assets/oka-provenance.json`.

**Q: Why did my build fail with `snapshot-engine-pairing`?**
Packaging validates the pairing the engine enforces at startup (ADR-0029
D2) — a mismatched debug-JIT engine / release-AOT snapshot is a red build
instead of an app hanging on the splash screen. Fix: rebuild the offending
side from the same Flutter SDK. Never bypass the check.

**Q: The device is fine but the ladder says INCONCLUSIVE?**
The device-health rung treats a wedged system UI, an unbooted device, or an
overloaded host as untrustworthy evidence — fix the device or use a fresh
one. Results from that state are not evidence.

## 🚢 Release Station

**Q: How do I cut a release?**
Merge conventional commits to `main`; release-please opens a Release PR that
bumps `VERSION` + `CHANGELOG.md`. The sync workflow derives pubspec/plugin
versions automatically. Merge → tag → pub.dev publish (automated). Full
runbook: [contribution guide](../contributing/contribution_guide).

**Q: How do I verify version consistency locally?**
```bash
just check-contracts   # VERSION == pubspec == plugin manifests; docs drift; changelog hygiene
just sync-version      # fix drift from VERSION
```

**Q: How do I prove a refactor produced a byte-equivalent artifact?**
```bash
oka compare old.apk new.apk          # exit 1 on differences
oka compare old.aab new.aab --quiet  # differences don't fail (CI-friendly)
oka compare a.apk b.apk --skip-badging   # zip entries only
```
Diffs `aapt2 dump badging` and the zip entry lists (crc32 content
comparison). The formal byte-equivalence gate for pipeline refactors
(ADR-0007) — a claim is a command, not a PR description.

## 🧪 Source-contract tests note

Tests that assert implementation details by reading source files (e.g.
`test/layout_validation_fail_test.dart`) encode invariants (no Gradle
fallback, layout validation must fail loudly), not just locations. When
moving code between files, update the paths in these tests.
