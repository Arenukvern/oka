# Process lifecycle: leases, teardown, `oka stop`

Every long-lived process oka spawns — an emulator, a browser session —
is recorded as a **process lease** (ADR-0018) and gets a declarative,
composable teardown path. This guide is the working manual: how to
declare lifecycle in your targets, how to inspect and stop processes,
and what an agent needs to know to operate all of it from the CLI alone.

The problem this solves: spawned processes used to leak. An emulator
booted by a timed-out run stayed up as an orphaned
`qemu-system-aarch64_headless`; browser debug sessions survived for
weeks. The fix is not a hook (crashes and `kill -9` bypass every hook)
but a **durable registry** — one JSON file per process under
`.oka_cache/processes/` — that later oka invocations reconcile against
reality.

## The mental model (30 seconds)

- **Lease** — an advisory record of one process oka spawned (or adopted):
  pid, kind, semantic identity (AVD, CDP port…), scope, ownership, and a
  graceful `stop_hint`. Not a supervisor; no daemon (ADR-0001 posture).
- **Scope** — `ephemeral` (die when the run ends; CI/agent default),
  `session` (die with the owning session), `persistent` (survive;
  explicit opt-in).
- **Ownership** — `owned` (the last run spawned it) vs `borrowed`
  (idempotent reuse found it running). **Teardown stops only owned
  leases.** Killing a borrowed session would break whatever terminal
  owns it.
- **Identity over pid** — every stop verifies the process is still the
  one the lease recorded (start-time token). A recycled pid is never
  signaled — that pid belongs to an innocent process now.

## For developers: declare lifecycle in your target

### Stop on exit (the common case)

Targets that boot a process can compose teardown declaratively — same
step contract as the build, so you get timeouts, artifact flow, and
structured events for free:

```dart
// One-shot CI/agent flow: boot, test, attempt verified teardown.
Oka(
  targets: [
    EmulatorTarget(apiLevel: 34, stopOnExit: true),
  ],
)
```

```dart
// Chrome sessions: an ephemeral-profile session ALWAYS tears down when
// the run ends (success or failure) — ADR-0017 §5. Persistent profiles
// (dev posture) survive the run by design.
Oka(
  targets: [
    ChromeSessionTarget(spec: chromeWebMcp(binaryPath: '/usr/bin/google-chrome')),
  ],
)
```

Teardown runs after the forward pipeline — on success **and** failure —
best-effort and bounded (`TeardownRunner`): a failing or hanging stop
step is reported as a warning and never masks the build result. That is
a hard law (ADR-0018 §2): cleanup errors must not corrupt the signal
your build already produced.

`TargetExecutionScope` installs signal handlers before target work. A signal
requests cancellation at the next pipeline step boundary: the current step
finishes publishing acquired handles, later steps are skipped, and one teardown
pass consumes those handles before exit. This does not interrupt a hung step;
step implementations still own timeouts for their host operations.

### Write your own teardown step

`Target.compileTeardown` is the same contract as `compile` — return
`BuildStep`s that consume the forward run's artifacts:

```dart
class MyTarget extends Target {
  @override
  List<BuildStep> compile(BuildContext ctx) => [BootSomethingStep()];

  @override
  List<BuildStep> compileTeardown(BuildContext ctx) => [
        StopEmulatorStep(),          // consumes `emulator-serial`
        StopChromeSessionStep(sessionName: 'main'),
      ];
}
```

Rules for teardown steps:

- Fail with `StepResult.failure('…')` and an actionable message; the
  runner collects it, the run still succeeds.
- Read upstream artifacts from `state` (e.g. `emulator-serial`, the
  chrome `…-pid` / `…-profile-dir` sub-handles) exactly like build steps.
- Guard any direct signal with identity verification:
  `verifyKillIdentity(liveness, pid, recordedToken)`. Raw pid-only kills
  are forbidden (pid recycling).

## For agents: inspect and control from the CLI

No new protocol — the CLI verbs are the intent surface, and `--json`
emits the standard pipeline-events envelope.

```bash
oka processes list            # human table: id, pid, kind, ownership/scope, verdict
oka processes list --json     # {"scope":"processes","event":"processes.inventory",...}
oka stop emulator-oka-emulator            # graceful (adb emu kill), identity-verified
oka stop chrome-main --force              # explicit borrowed-lease override
oka stop --stale                          # drop provably-stale records only
oka doctor                                # includes a [Process Leases] audit block
```

### Inspect and reconcile managed session state

Session-state leases track managed browser-profile or emulator state separately
from process leases. Listing and inspection are read-only; reconciliation and
explicit close are dry runs (previews) by default:

```bash
oka session-state list
oka session-state inspect <id> --verbose
oka session-state resume <id>                 # explicit provisioning retry
oka session-state reconcile                 # preview eligible ephemeral cleanup
oka session-state reconcile --apply         # apply that cleanup
oka session-state close <id>                # preview explicit close
oka session-state close <id> --apply        # close after fresh safety checks
oka session-state forget <id>               # preview record-only recovery
oka session-state forget <id> --apply       # remove the record only
```

`reconcile --apply` removes only Oka-owned ephemeral project resources that
providers positively identify as unused. Persistent or session-retained state,
borrowed resources, active resources, and inconclusive findings stay retained.
`close <id>` is the explicit path for retained state, but still refuses cleanup
unless ownership and inactivity checks pass. Neither command stops the
associated process. Review the preview before applying; use
`inspect <id> --verbose` to see inspector findings. `list` reports lease IDs
and workflow versions, which you can copy into `inspect` or `close`.
Applied cleanup reports repeat the safety boundary: process identity and
provider markers do not prove every detached child or concurrent opener is
absent, and path checks cannot prevent same-user filesystem races.

On Windows, Chrome managed profile acquisition and launch setup are supported
using the profile directory's inherited ACL. `dart:io` cannot verify those
ACLs, so all destructive session-state directory cleanup remains report-only
on Windows. Linux/macOS managed directories retain POSIX `0700` enforcement.

If provisioning failed, its `partial` lease remains durable. `resume <id>` is
an explicit, non-preview action: it reruns the exact composed workflow from the
beginning, so provision steps must be idempotent. Resume accepts only
`reserved`, `provisioning`, or `partial` Oka-owned directory leases with the
exact workflow version available. The previous Oka owner and any associated
process must be verifiably stopped (or the owner must be this process), the
reservation and ownership evidence must match, and every workflow inspector
must affirm unused. A missing inner ownership marker is repairable only when
the verified reservation exists and the existing directory is empty. Any
failed provisioning attempt remains `partial`; unknown, busy, or unverifiable
state is refused without retrying.

The CLI composes the current Chrome-profile and Android AVD workflows, but
resume is intentionally limited to Oka-owned directories. Android AVD leases
are caller-owned opaque inventory records, so they cannot be resumed by this
operation. For a refusal, use `inspect <id> --verbose`, stop the owning process
cleanly if it is active, and restore the exact workflow composition; do not
delete markers or profile contents to force a retry.

`close` can reclaim same-host state left across a reboot only when ownership and
current provider checks still affirm that the resource is unused. If the
resource is positively absent, `forget` removes only its registry record; it
does not delete a resource or reservation marker. Both operations preview by
default.

If a lease is retained, check its reason and findings before retrying; close the
owning browser cleanly and inspect again rather than deleting its profile or
registry record by hand. For registry issues, keep the reported path/message,
check `oka cache --details --kind session --kind browser-profile`, and use
`oka doctor` / `oka processes list` for the separate process-lease view.
Unknown or malformed ownership is intentionally a stop-and-investigate case,
not permission to delete.

Reading `oka processes list` output:

```text
emulator-oka-emulator  pid 4242  android-emulator  owned/ephemeral  running  (avd=oka-emulator serial=emulator-5554)
chrome-main            pid 0    chrome-session    borrowed/ephemeral  identity unknown  (cdp_port=9222)
```

- `running` — live and identity-verified.
- `stale (process gone)` — the process exited; the record is safe to
  drop (`oka stop <id>` or `oka stop --stale`).
- `stale (pid recycled)` — the pid now belongs to a *different* process.
  **Never killed by oka.** Only the record is removed.
- `identity unknown` — oka could not verify; reported, kept, never
  signaled by PID. PID zero also means unknown. Explicit semantic stop hints
  may be used; borrowed leases require `--force`, including PID-zero leases.

On Linux, Oka's process identity token now includes the kernel boot UUID as
well as `/proc/<pid>/stat` start ticks. Older process leases contain only the
start ticks and therefore cannot authorize a signal after this change. If an
older lease refers to a process that is still running, stop it through its
owning application or process manager; Oka will not guess from the PID.

### The JSON contract (stable, for tooling)

- `oka processes list --json` → one `processes.inventory` event with a
  `leases` array (each lease = the on-disk JSON plus a `liveness`
  field: `live | dead_pid | reused_pid | unknown`).
- `oka stop <id> --json` → one `stop.result` event with
  `ok`, `action` (`stopped | record_dropped | refused | failed`), and an
  `error` string when refused/failed — always actionable, naming the law
  that refused the stop.

Agents can also read the leases directly:
`.oka_cache/processes/<id>.json` is plain JSON (the registry is the SSOT
and survives oka crashes).

## What happens on crashes

`kill -9`, a Dart crash, a closed laptop — no handler runs, but the lease
file survives. The **reconcile sweep** (`oka doctor`, `oka stop --stale`,
and explicit reconciliation) checks records against the host. Inventory reads
only report state; they do not delete records. During reconciliation:

- provably stale records (process gone, pid recycled) are dropped;
- live leases are classified and **reported, never auto-stopped** —
  oka's reuse posture deliberately keeps your dev emulator up, so an
  orphaned-looking emulator is flagged (`oka stop <id>` is the explicit
  stop);
- hermetic harnesses (CI tiers) opt into harder behavior:
  `stopOrphans` stops orphaned owned+ephemeral leases through the same
  identity-graded laws.

Foreign orphans (e.g. leaks from `flutter run`'s own Chrome sessions)
are *reported* by `oka doctor` context but never killed — oka only ever
reconciles its own leases.

## Adding a new session kind

A new long-lived process kind (iOS simulator, container, server) owes
the system exactly two small pieces, not new mechanics:

1. Write a lease at spawn (`ProcessLeaseRegistry.upsert`, one record per
   the ADR §1 JSON shape) — with a semantic `identity` entry and a
   graceful `stop_hint`.
2. Provide a stop step that consumes your handle artifact, and compose
   it from `compileTeardown` when the kind is ephemeral-by-default.

Everything else — discovery (`oka processes`), stopping
(`oka stop`), reconcile, doctor — follows for free.
