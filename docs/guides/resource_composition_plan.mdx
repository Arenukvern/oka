# Declarative resource composition — design and execution plan (ADR-0026)

**Status:** design direction accepted (amended 2026-09-27); R0 done,
implementation started.

This plan tests whether a reusable composition contract can serve Oka,
`ecsai_harness`, the Flutter MCP toolkit, IntentCall, and the collector
monorepo without flattening their different process, session, and
supervision semantics. It does not approve a resident service. The R0
survey ([evidence](../evidence/process-lifecycle-r0-survey-2026-09-27))
narrowed the ambition: a shared **vocabulary**, one **zero-dependency
contract package**, and one **process platform seam** in `oka_core` — not a
large shared SDK.

## Goals and constraints

- Let developers declare components, dependencies, readiness, lifecycle,
  outputs, and diagnostics as typed, immutable values.
- Readiness is a typed declaration (dialect, budget, parsed outputs);
  probe mechanics stay provider-internal.
- Provider implementations are independently replaceable or
  user-implemented; customization is constructor injection, never string-key
  plan surgery.
- Treat crash observation and reconciliation as general lifecycle behavior;
  make durable leases optional for resources that outlive their creator —
  but the pre-side-effect durable handle write is contract.
- Keep MCP/ACP as protocol adapters; do not make them the process manager.
- Preserve Oka's lease identity, owned/borrowed, teardown, and no-daemon
  laws.
- Supervision stays vocabulary-only: no phase may require a supervisor to
  exist.

## API shape to validate

The developer experience is a declarative graph assembled from named const
values plus an explicit provider selection. Illustrative only; names are
not frozen:

```dart
final port = OutputRef<int>('collector.port');

final composition = Composition(
  components: [
    Component(
      id: 'collector',
      provider: CollectorProvider(),
      readiness: HandshakeLine(
        pattern: 'ready ',
        parse: (line) => {'collector.port': int.parse(line.split(' ')[1])},
      ),
      lifecycle: const Lifecycle(scope: ResourceScope.session),
    ),
    Component(
      id: 'agent',
      provider: HarnessProvider(),
      dependsOn: const ['collector'],
      requires: [port],
      readiness: const FilePresent('.harness/session.json'),
    ),
  ],
  evidence: const JsonlEvidenceSink(),
);

final report = composition.validate(); // pure — no side effects
```

Concerns the contract must distinguish:

| Concern | Contract question |
|---|---|
| Composition | What components exist, what depends on what, and what typed output promises flow between them? |
| Provider | How does this component start, attach, become ready, stop, and reconcile — and which capabilities does it declare? |
| Process seam | How are bounded runs, tree-aware stops, and pid identity done on this OS? (`oka_core`) |
| Evidence | Which lifecycle events and bounded output taps are captured, with which terminal causes? |
| Persistence | Does this component write the durable pre-side-effect handle because it can outlive its creator? |

## Phases and gates

### R0 — Cross-project case inventory — **done 2026-09-27**

Five systems surveyed (oka, `ecsai_harness`, the Flutter MCP toolkit,
IntentCall, one anonymized collector monorepo) plus a recorded working
session. Evidence:
[process-lifecycle R0 survey](../evidence/process-lifecycle-r0-survey-2026-09-27).

**Gate (amended, falsifiable):** the common contract expresses oka's
identity-before-signal, the collector monorepo's never-reclaim-on-guess,
and the Flutter toolkit's file-absence-liveness with **≤ 2 per-provider
escape hatches**; more than 2 ⇒ narrow the contract before any package
grows. Outcome: passed with narrowing — vocabulary + one contract package +
one platform seam; supervision and shared probe mechanics cut.

### R1 — Contract and state model

Specify and review, as code and fixtures (not prose agreement):

- Immutable component values; dependency, cycle, capability, scope, and
  output-promise validation (`Composition.validate` / `explain`).
- Readiness dialects as typed values with composition-declared budgets and
  pure decoders into `OutputRef<T>`; unready blocks `dependsOn`.
- Lifecycle states and structured transitions, including failed, crashed,
  stopped, and `unknown`; **terminal causes** (`exited`, `signaled`,
  `killedOnDeadline`, `providerFault`, `transportLost`, `unknown`).
- Bounded log taps + lifecycle-event JSONL as the day-one evidence surface;
  retention/redaction policy frameworks deferred.
- The durable pre-side-effect handle: typed, schema-versioned, removed at
  exit = liveness, one typed secondary probe; registry/adoption machinery
  optional behind capabilities.
- No `Future.timeout` over a live child anywhere in the contract or
  reference providers.

**Gate:** the contract package's own test suite pins the semantics above
with scripted fakes; a fixtures file records the frozen invariants for
copy-friendly adoption by non-oka consumers.

### R2 — Platform seam and contract package — **in progress**

Two artifacts:

1. **Process seam in `oka_core`** (`process_tree`, bounded runs):
   descendant enumeration, tree-aware stop (enumerate **before** killing
   the root; escalate SIGTERM→SIGKILL; verify death), bounded
   run-with-deadline that kills instead of abandoning, pid+start-token
   identity reuse. `SystemProcessRunner` stops abandoning children on
   deadline.
2. **`packages/resource_composition`** — zero-dependency, vendor-neutral
   contract package: components, readiness dialects, `OutputRef`,
   lifecycle values, terminal causes, events, bounded taps, the provider
   interface, validation/explain, and scripted fakes.

**Gate:** parent→grandchild fixture asserts zero survivors after forced
teardown on macOS and Linux (a surviving grandchild ⇒ the seam stays
per-repo and the vocabulary-only verdict hardens); contract tests prove
invalid graphs fail before start, event order under a fake run, and that
swapping a provider or evidence sink does not edit unrelated components;
`explain` provably performs no side effects.

### R3 — Cross-project adapters

Prototype adapters without changing ownership boundaries:

1. An Oka adapter maps the common concepts onto `ProcessLeaseRegistry`,
   `ProcessSurface`, and `TeardownRunner`, preserving identity
   verification, borrowed-resource protections, and cleanup that never
   masks the primary result.
2. An `ecsai_harness` adapter proves a non-Oka provider can use the same
   contracts.
3. An IntentCall adapter exposes ACP/MCP handles as a component capability;
   protocol internals stay in IntentCall.
4. The Flutter toolkit consumes the contract package's runner-session types
   behind its existing `dependency_overrides` bridge; the bridge is removed
   on publish (release-blocking debt by construction, ADR-0027).
   **Status 2026-09-27:** `flutter_mcp_harness 0.1.0` published; the bridge
   is retired and oka_harness resolves it hosted.

**Gate:** at least two provider implementations pass the same contract
tests, and each adapter **deletes more failure-prone code than it adds**
(concretely: retire a stderr magic-string scrape, a `Future.timeout`
abandonment vector, or a per-site timeout constant — an adapter that only
demos fails this gate). Copy-friendly fixtures round-trip without importing
the package.

### R4 — Failure, recovery, and evidence hardening

Exercise the failure classes from the survey (F1–F6):

- Child exits cleanly, exits nonzero, is signaled, crashes, or is killed
  while the composing client is still running.
- Composing client crashes or is forcibly terminated; a later invocation
  reconciles observed state.
- Identity is stale, PID is reused, a handle is missing/corrupt, or the
  resource is borrowed or externally managed.
- Two compositions race to start, attach, stop, or reconcile the same
  resource.
- Readiness times out, a stop hangs, a grandchild survives the first rung.
- Output contains secrets; logs grow; evidence retention is bounded.

Unknown identity must remain unknown; it must never silently grant kill
authority.

**Gate:** tests prove safe behavior under each supported failure class;
platform-dependent claims carry real host evidence or are labeled pending
(the repo's standing Windows-evidence rule applies to the seam's Windows
path).

### R5 — Package boundary review

Pre-declared default (checkpoint decision 2026-09-27): **a small common
contract plus adapters** — `packages/resource_composition` stays
zero-dependency and vendor-neutral so the Flutter toolkit can consume it
without violating its no-oka-references law; the process seam stays in
`oka_core` and is documented as copy-friendly. Re-open the boundary only if
a real consumer demonstrates a pain copying cannot solve. Supervisors are
evaluated only if continuous desired-state enforcement is demonstrated by a
real user; none was found in R0.

**Gate:** the boundary decision names ownership, versioning, compatibility,
security, and support boundaries; any future optional supervisor passes the
same provider contract without altering the component graph.

## Verification matrix

| Claim | Evidence required |
|---|---|
| Declaration is compositional | Tests replace one provider/evidence sink while keeping unrelated component values unchanged |
| Plan is safe to inspect | `explain`/`validate` tests prove no process or network side effects |
| Recovery is general | Crash/reconcile tests across short-lived, long-lived, adopted, and external resources |
| Leases are optional, handles are not | A command-scoped process works without durable state; an outliving resource writes the pre-side-effect handle |
| Deadline kills, never abandons | Bounded-run tests assert zero surviving descendants after timeout (macOS/Linux; Windows pending) |
| Death has a meaning | Terminal-cause fixtures cover exit, signal, deadline-kill, provider fault, transport loss, unknown |
| Diagnostics are useful and safe | Failure fixtures cover bounded output, readiness history, and redaction-before-persistence |
| Oka remains compatible | Existing process lease, teardown, no-daemon, and identity-safety suites remain green |

No phase is considered complete from design prose alone. Implementation
phases and their gates are tracked in
[`PHASE_CHECKLIST`](../PHASE_CHECKLIST).
