# Internal product delivery programme

The first product is Last Answer. It consumes ecsai_harness; both consume
Oka. Oka's immediate customer is the internal development loop. External
customer readiness follows sustained internal use, not the existence of APIs.
The Android delivery horizon is 2026-11-20; the first operator uses macOS
locally. This programme preserves the broader shared-document acceptance
journey in Last Answer's `docs/PLAN.md` and the harness's central plan.

## Acceptance journeys

| Requirement | Evidence needed before calling it complete |
| --- | --- |
| Develop Last Answer, the harness, and Oka through Last Answer | A real task in each repository: scoped delegation, attributed source change through ordinary coding tools, independent check, reviewable diff and permission controls, recovery, then a distinct second task |
| General project workspace | Declared checks/build/server operations for different project stacks, correct cwd/argv/environment, bounded cancellation, retained failure output; no candidate accepted using an unrelated owner-tree check |
| General browser window | Actual native rendering of plain HTML/JS, a framework app, redirects/history/reload and errors; navigation does not acquire server ownership; browser content gains no application capabilities |
| ECS delegation through MCP | Actual caller → admitted internal actor → selected model inference → independently checked result; correct status/cancel/recovery, then two disjoint concurrent tasks with observable attribution |
| App-open automations | A command job and an ECS-backed job run from saved declarations; explicit enable/pause/cancel, finite budgets, no duplicate scheduling, owned teardown, restart history; no claimed execution after app exit |
| World management and observability | The operator sees work, owners, claims, messages, model choice, failures and proposals in Last Answer, and can issue/cancel work through the same authoritative world |
| Fast Dart feedback | Matched cold/warm measurements in actual consumer repositories, cache invalidation across neighboring path packages, failing controls, conventional test parity; Flutter suites remain in their native lane |
| AI-native application control | Flutter toolkit/harness and universal automation can discover and operate real app capabilities, observe results and errors, and repeat a checked journey without hidden UI-only state |
| Android paired companion | A real device joins the intended shared workspace; state/authority survive reconnect; unsupported local execution is explicit |
| Android release | No-Gradle release AAB with complete dependencies/resources, correct manifest, release signing, artifact verification, device startup/first frame, product QA and store-ready assets |
| Daily internal adoption | Repeated ordinary work uses the delivered paths; retained incidents are resolved and measured, rather than replacing adoption with fixture success |

  harness wrapper consume it. Neighboring package sources participate in the
  content key. Native conventional tests remain the acceptance oracle.
- `oka_core/project_operations.dart` owns declared project commands and browser
  server sessions. Last Answer composes it instead of owning another executor.
  Physical command cancellation now uses the bounded run's existing stop owner.
  Ordinary dialog cleanup now refuses close after unverified cleanup and retains
  an actionable recovery receipt and retry. The 24 focused session, shutdown and
  widget tests passed, including real process cancellation; installed-app
  qualification remains open.
- `oka_supervisor` exposes app-scoped convergence with cancellation, logs and
  process-generation ownership. Last Answer command execution is integrated;
  ECS-backed automation is being wired through its existing client.

  A seven-stage live run observed reload, error/recovery and back/forward,

  need qualification. React/npm is an example profile, not the renderer.

  admission, persistence and worker composition. Source tests pass. The live
  owner has been gracefully transitioned: final snapshots were saved, the same
  participant/claims restored, and the requested MiniMax palette entry is live.
  The first read-only delegation exposed a project-scope defect (realm storage
  was reported as the project root) and was cancelled. Harness ADR 0112 owns
  immutable attachment-to-task project binding; internal staffing remains
  unqualified until that path works and its full acceptance sequence passes.
  Host admission now retains independent project leases for the same grant;
  focused membership/root/revocation tests pass. The actual Codex mount is
  still diagnostic/unjoined. Scoped worker execution and mounted qualification
  remain required; source-level admission is not live acceptance.
  After the requested Codex reconnect, its diagnostic still reported the old
  seat process and exhausted identity admission. Restored admission/scope,
  model-pin and identity-recovery changes passed 11 focused tests. Project-local
  execution now replaces the unconditional multi-project refusal in source;
  loaded-owner adoption and actual mounted execution remain unqualified.
  Two focused projection tests now
  verify distinct project maps and membership revocation without reading the
  world-level filesystem map. Two Pi baseline procedures swapped
  live source despite the ownership contract; those comparisons are excluded
  from evidence, the offending backend worker was stopped, and subsequent
  provenance work is restricted to isolated candidate files.
  The materialization-plan experiment is retired by the operator's decision.
  Ordinary delegated coding uses search, read, exact-text edit/write and command

  The seat AOT builds, but the owner snapshot currently fails on a neighboring

## Parallel work and scale-up

Pi workers use the explicitly requested
`openrouter/minimax/minimax-m3.1-flash:free` selector through the Pi MCP
connector. Initial lanes are Android dependency resolution, Last Answer agent
automation, and read-only live ECS qualification. The parent owns integration,
native runtime verification and consumer builds. Workers must retain foreign
changes and report precise validation limits.

Start ECS staffing with one bounded read-only task. Verify the actual model,
terminal result and attribution. Follow with one scoped source task and an
independent check. Then allow two disjoint tasks; increase concurrency only
when ownership, completion, cancellation and integration remain observable.
An unavailable model or stale owner is a named failure, not permission to
change participant identity, start a second owner, or silently choose a model.

## Delivery order

1. Close the live delegation and native browser feedback loops while repairing
   Android release dependencies in parallel.
2. Complete command and ECS app-open automations; connect world work/status
   controls to the same live authority and retain outcomes across restart.
3. Run real self-development tasks across all three consumers and different
   project stacks. Measure speed and retain failing/conflicting controls.
4. Qualify paired Android operation, signing, startup and product journeys.
   Polish visual work and observability against those real journeys.
5. Resolve the retained internal incidents and perform the complete release
   audit. Store publication requires the concrete reviewed release artifact;
   a debug-signed bundle or a passing unit suite is not completion.

Completed implementation details belong in dated evidence and owning ADRs
(Oka 0048–0050, Last Answer 0020–0022, harness 0110). Keep unresolved product
obligations here until evidence meets the corresponding acceptance journey.
