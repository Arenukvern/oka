# Cache storage and cleanup

See where storage goes across known projects, then reclaim reproducible caches:

```bash
oka cache
oka cache clean --apply
```

The overview shows the largest locations and reclaimable storage. The second
command deletes eligible build and shared dependency caches across known
projects. The next build recreates them and may need network access. Run
`oka cache clean` without `--apply` to preview the paths first. Neither command
stops sessions or deletes emulator user data.

## Find your existing projects

Builds automatically remember their project locations. To include older projects,
scan the directory where you keep your repositories once:

```bash
oka cache --scan "$HOME/projects"
oka cache clean --apply
```

Repeat `--scan ROOT` for multiple locations. Discovered projects with existing
`.oka_cache` directories are remembered in `~/.oka/cache-projects.json`, outside
prunable storage. Missing caches are skipped on later runs. **Known projects
does not mean every project on the disk**: Oka does not search unrelated drives.

Discovery skips hidden and generated directories (`node_modules`, `build`,
`Pods`, `vendor`), with limits of 12 levels and 50,000 visited directories.
Explicit root aliases are resolved to canonical paths; symbolic links encountered
inside a scan are skipped. Warnings identify incomplete scans. Supply a more
specific `--scan` root to include a project under an excluded directory.

`--global` explicitly selects the default global view. `--project PATH` narrows
the project portion to one directory; shared storage remains global. Use
`--scope build` as well when cleanup must affect only that project's outputs.

## Review before deleting

```bash
oka cache clean                          # preview; does not delete
oka cache clean --interactive            # review and confirm in a terminal
oka cache clean --save-plan cleanup.json
oka cache clean --apply-plan cleanup.json
```

Ordinary `--apply` recalculates selection. A saved plan applies only its selected
paths after rediscovering ownership and session protections and checking size,
file count and latest modification time. Changed or newly protected locations
are skipped; newly discovered caches are never added. These measurements are
change checks, not content hashes or a lock against concurrent writers.
Save plans outside the selected cache directories, using a path without symbolic
links. Existing plan files are never overwritten.

Only explicit `--interactive` prompts, and it requires terminal input and output.
It rejects `--json` and pipes; agents can use saved plans instead. `--dry-run`
explicitly requests preview and cannot be combined with `--apply`.

## Select what to reclaim

```bash
oka cache --details                      # every location and diagnostic record
oka cache clean --project example --scope build --apply
oka cache clean --scope shared --max-size 2GB --apply
oka cache clean --scope tools --older-than 30d --apply
```

The budget applies only to eligible locations in the selected scopes, not total
machine storage. Selection removes age matches first, then oldest remaining
locations until that pool fits the budget. Without an age or budget, all eligible
locations in scope are selected. Units are shared-store categories and build-mode
directories (split when needed to preserve profiles); a large unit can reclaim
more than the requested difference.
`--older-than` uses latest filesystem modification time, **not last-use time**.
Sizes accept bytes or binary K/M/G/T, KB/MB/GB/TB and KiB/MiB/GiB/TiB suffixes.

Stats reports **logical file bytes**, not filesystem allocation. Sparse emulator
disks, compression and hard links can make these totals differ from `du` or free
disk space. Overlapping paths are deduplicated in the overall total. Links are
not followed. Incomplete scans carry warnings and are not eligible for pruning.

## What the inventory covers

| Storage | Prune behavior |
|---|---|
| Known projects' `.oka_cache/build/` (or the explicitly selected project) | Build scope; browser profiles remain |
| Shared store at `OKA_CACHE` or `~/.oka/store` | Shared scope |
| Existing legacy Maven/AI directories | Shared scope |
| Oka tools at `~/.oka/tools` | Explicit tools scope, one unit per tool (`tools-r8`, `tools-kotlin-*`, `tools-bundletool.jar`, …) when the platform packages supply tool guidance; otherwise one coarse unit. Notes name the `oka get` command to re-provision |
| Managed and configured Android SDK components | Report only, including system images and emulator binaries |
| Android AVD directories and custom locations referenced by `.ini` files | Report only; these contain user data and snapshots |
| Apple simulator devices and known runtime directories on macOS | Report only |
| Browser profiles and project process/session records | Preserved |
| Dart Pub cache and Flutter cache when `FLUTTER_ROOT` is set | Report only; shared with external tooling |

Android discovery honors configured SDK and AVD environment paths. Apple
simulator storage is host-specific; filesystem inventory does not indicate
whether a device is running. Stats includes management guidance: Android Device
Manager/`avdmanager` for virtual devices, `sdkmanager` for SDK packages, and
Xcode/`simctl` for Apple simulators. Oka does not treat their data as disposable
build cache. An absent path is omitted rather than reported as installed.

Recorded live or uncertain project sessions prevent build pruning. Inspect
`oka processes list` to resolve them. Stop builds before pruning; process records
are advisory and cannot detect every external writer. Deletion rechecks the
selected directories and skips changed or unsafe locations. Only successful
deletions count toward the reported freed logical bytes.

## For agents and automation

```bash
oka cache schema                         # machine interface; no storage scan
oka cache --json                         # full inventory and discovery coverage
oka cache clean --save-plan cleanup.json --json
oka cache clean --apply-plan cleanup.json --json
```

JSON includes versioned schemas, totals, warnings, project coverage and
`next_actions` with argument arrays and working directories. Execute those arrays directly rather than
constructing shell strings. The same typed core operations power the CLI, so
agents do not need a separate MCP server or interactive session. An MCP adapter
can later wrap the contract without implementing another cleanup policy.

## Inspect devices, profiles, sessions and registries

```bash
oka cache --details
oka cache --kind session --kind browser-profile
oka cache --kind registry --json
```

The default overview includes diagnostic counts; details keeps small metadata
records visible regardless of storage size. `--kind` filters diagnostics and
implies details. JSON retains the complete storage inventory and totals alongside
the filtered `diagnostics` report (`oka.cache.diagnostics.v1`).

| Record | Information |
| --- | --- |
| Android emulator | AVD name, API, ABI, system image, userdata/snapshot logical bytes and related recorded sessions |
| Apple simulator/runtime | Stored name, identifier, runtime/device type or bundle version where a plist is available; logical bytes |
| Browser profile | Individual Oka profile directory, persistence, logical bytes, CDP port and related project/session IDs |
| Session | Lease kind, PID, ownership, scope, start time, selected identity fields and identity-checked process liveness |
| Registry/project | Metadata path, schema status, recorded paths including missing caches, malformed-record issues and selected project cache state |

Observations state their source and timestamp. Stored device state does not
establish that a device is running; PID zero means unknown. ADB, CDP and simctl
semantic runtime probes are not included. Apple plist decoding uses a bounded,
read-only `plutil` conversion on macOS; callers can inject another decoder.

New Chrome leases retain their profile directory, including temporary profiles.
Older leases without that information report unknown attribution. Only recorded
or discovered Oka profiles are included. Browser databases are not read. Raw
owner command strings and arbitrary lease identity fields are omitted from the
default report. Global coverage remains known projects, not all applications.

Ordinary stats does not register projects or repair metadata. Explicit `--scan`
still remembers projects. Malformed registry entries become diagnostic issues
while valid entries remain visible; cleanup still rejects invalid registry
metadata. Diagnostics never reconciles leases, stops processes or deletes data.

## Clean cache without removing managed session state

Use `oka session-state` for managed browser-profile state; cache pruning is not
session cleanup:

```bash
oka session-state list
oka session-state inspect <id> --verbose
oka session-state resume <id>                 # explicit failed-provision retry
oka session-state reconcile                 # preview only
oka session-state reconcile --apply         # remove eligible ephemeral state
oka session-state close <id>                # preview explicit close
oka session-state close <id> --apply
oka session-state forget <id>               # preview record-only recovery
oka session-state forget <id> --apply       # remove the record only
```

Reconciliation applies only to Oka-owned ephemeral resources with positive
unused findings. Persistent state, active or uncertain profiles, and registry
issues are retained. `oka cache clean` preserves browser profiles and session
records. The legacy `oka clean` cleans unrelated cache contents while preserving
registered managed resources and their reservation markers. If the registry
cannot be inspected safely, contains issues, or a registered resource or marker
path cannot be resolved safely, `oka clean` refuses before deleting cache
contents rather than guessing. It does not substitute for `session-state close`.
When session-state paths are present, cleanup output notes that this protection
is path-based: it prevents ordinary cleanup from selecting known active or
disposing state, but it is not a security boundary against another process
running as the same user and racing filesystem checks with deletion.

Managed Chrome profile creation works on Windows and uses the parent directory's
inherited ACL. `dart:io` does not inspect or verify those ACLs. POSIX managed
directories continue to be restricted to mode `0700` on Linux/macOS. All
destructive session-state directory cleanup remains report-only on Windows;
Windows profile creation does not enable Windows cleanup.

When cleanup is retained or refused, inspect the lease with `--verbose`, close
the browser normally, then preview again. Use `oka cache --details --kind
session --kind browser-profile` for related inventory records and `oka doctor`
or `oka processes list` to investigate process leases. Do not manually remove
profiles or registry entries to bypass an unknown-use or ownership finding.
Use `forget` only when the recorded directory is confirmed absent; it removes
the registry pointer, not any profile data or marker.

### Workflow composition and CLI code loading

Project entrypoints can compose their actual provider workflows with `Oka`:

```dart
import 'package:oka_android/oka_android.dart';
import 'package:oka_core/oka_core.dart';
import 'package:oka_web/oka_web.dart';

Future<void> main(List<String> args) => okaRun(
  args,
  oka: const Oka(
    pipelines: [
      AndroidPipeline(
        config: AndroidBuild(packageName: 'dev.example.app'),
      ),
    ],
    sessionStateWorkflows: [
      chromeProfileStateWorkflow,
      androidAvdStateWorkflow,
    ],
  ),
);
```

When a `ChromeSessionTarget` or `EmulatorTarget` appears in `Oka.targets`, it
contributes its configured session-state workflow automatically. Use the
explicit `sessionStateWorkflows` list for project workflows that are not owned
by a target; the same workflow instance is deduplicated if listed both ways.

When an entrypoint is discoverable, `oka session-state inspect`, `resume`,
`reconcile`, `close`, `forget`, and `oka doctor` run their operation inside
that entrypoint process, using its composed workflow objects. The hidden
`--oka-session-state` protocol accepts a JSON request with `protocol_version: 1`,
an operation, and (where needed) `lease_id` and `apply`; it replies with a
versioned `oka.session-state.protocol.v1` JSON response in a single stdout
frame prefixed by `\x1eOKA_SESSION_STATE_V1:`. Other entrypoint stdout is ignored;
missing, duplicate, or malformed frames fail closed. Only request data and
report JSON cross the process boundary: workflow closures and provider
instances are not serialized, and registry workflow IDs never trigger package
loading.
An unsupported protocol version or a required workflow missing from the
composition is an error; Oka does not guess or load code based on registry
contents. `oka session-state list` is registry-only and does not need workflow
code.

Entrypoint discovery is the normal `oka.yaml` `pipeline.dart_entrypoint`, then
`tool/oka_pipeline.dart`, then `bin/oka_pipeline.dart`. Without an entrypoint,
the CLI retains its first-party Chrome-profile and Android-AVD workflow
fallback. Custom workflows absent from that fallback remain unknown/retained.
Core contracts remain provider-independent; project entrypoints import the
provider packages they choose to compose.

## Compose inspection in Dart

Platform and package authors implement `CacheDiagnosticProvider` and compose it
with first-party providers. No CLI switch registration, subprocess JSON parsing,
build execution or MCP dependency is required.

```dart
import 'dart:io';
import 'package:oka/oka.dart';

Future<CacheDiagnosticReport> inspectCaches() async {
  final workspace = await loadCacheWorkspace(inspection: true);
  final storage = await workspace.inventory.scan();
  return CacheDiagnostics(
    providers: [
      ...defaultCacheDiagnosticProviders(),
      // MyPlatformDiagnostics(),
    ],
  ).inspect(CacheDiagnosticContext(
    projects: workspace.projects,
    environment: Platform.environment,
    storage: storage,
  ));
}
```

For a dependency-light package, import `oka_core` and compose
`CoreCacheDiagnosticProvider` plus providers exported by `oka_android` or
`oka_web`. Supply explicit canonical project paths and a `StorageReport` from
your own `StorageInventory`. Context environment, observation time and process
liveness are injectable. Providers return `CacheDiagnosticContribution` with
typed records, observations, inert actions and structured issues. Kinds are open
strings; provider metadata is namespaced by provider ID in JSON. Provider or
record ID collisions and provider failures become issues without replacing
valid records. Additional providers never grant cleanup permission.

The first-party composition and workspace loader are exported by `oka`.
Device/profile sub-measurements explain storage; they are not added again to
the overall total. Recorded temporary profiles outside discovered storage appear
in diagnostics only. Future MCP or interactive views can consume this report.

## Compatibility commands

`oka cache stats` is an explicit alias for the overview; `oka cache prune` is an
alias for `oka cache clean`. Both retain their options and JSON interfaces.
Their default project coverage is now all known projects; use `--project PATH`
to explicitly keep a single-project selection.

`oka cache list [--json]` and `oka cache why <category[/name[/version]]>` inspect
**indexed shared-store entries only**. Their totals exclude index metadata;
stats measures all files in discovered directories, including unindexed files.
Maven resolution uses `<store>/maven`, with `~/.oka/cache/maven` as a compatibility
fallback when the store's Maven directory is absent.

`oka cache gc --older-than 30d --dry-run` previews indexed-store GC. Unlike
`prune`, existing `gc` executes unless `--dry-run` is supplied, uses entry
**creation** age, and requires an explicit age or budget. Prefer `cache clean` for
cross-location cleanup.

`oka clean` (without `cache`) cleans unrelated contents of the project's
`.oka_cache`; registered managed session-state resources and their reservation
markers are preserved, not a reason to refuse the entire cleanup. If registry
inspection or protection is incomplete, it refuses before deleting cache
contents. `--full` also cleans unrelated dependency-cache contents; it is not an
all-storage cleanup command. Prefer `oka cache clean` to preserve browser
profiles and process records.
