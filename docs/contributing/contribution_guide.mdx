# Contributing

Thanks for your interest in oka! The project is agent-first: agents execute,
humans steer. That shapes how contributions work.

## Setup

Install Dart 3.13 or newer and `just` for the contributor tooling. Real Android build tests also need
Flutter and the Android SDK; see the [build guide](../guides/build_and_config).

```bash
git clone https://github.com/Arenukvern/oka.git && cd oka
just install    # workspace dependencies (excludes the Flutter example)
just test       # dart test
just lint       # dart analyze
```

Repository stewardship tools are implemented in Dart; shell commands are
entry points. The release and documentation gates use only the Dart SDK and
can run before dependency installation. See [`AGENTS.md`](../../AGENTS.md).

## Ground rules

1. **Non-negotiables** (see `AGENTS.md`):
   - The default build path must never shell out to `flutter build apk` /
     Gradle as success.
   - Only the no-Gradle pipeline exists; no cargo/Gradle fallbacks (ADR-0009).
2. **Behavior SSOT is code + tests.** Docs link to implementation; they never
   paraphrase it.
3. **Design forks need an ADR first.** If your change settles a trade-off,
   open/propose an ADR in `docs/decisions/` before coding.
4. **Phases are done only with evidence.** Update
   [`docs/PHASE_CHECKLIST.mdx`](../PHASE_CHECKLIST) with test references.

## Docs sync

After any behavior change, update the matching doc layer — see
[`docs/start_here/docs_map.mdx`](../start_here/docs_map):

| Change type | Update |
|---|---|
| Internal trade-off / architecture | `docs/guides/design_faq.mdx` Q&A and/or new ADR |
| Public API / usage / config key | `docs/guides/build_and_config.mdx` (copy-paste valid) |
| Settled strategic decision | `docs/decisions/NNNN-*.md` + index row |
| Phase-level completion | `docs/PHASE_CHECKLIST.mdx` evidence table |

## Commit messages

Use [Conventional Commits](https://www.conventionalcommits.org/) so
[release-please](https://github.com/googleapis/release-please) can build the
changelog and version bumps:

- `feat:` — new capability (minor bump)
- `fix:` — bug fix (patch bump)
- `docs:` — documentation (patch bump when it is the only change in a release)
- `perf:` — performance improvement
- `chore:` / `refactor:` / `test:` — hidden in the generated changelog

## Releases

Releases are automated on `main` via **release-please**. Configure the existing
`RELEASE_PLEASE_TOKEN` secret for release PR creation and sync pushes when
those events need to trigger subsequent CI runs automatically. With the
repository-token fallback, PR workflow runs may require approval and tag pushes
do not start the publication workflow. See [GitHub workflow trigger rules](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow).
The sync workflow also runs its contract checks after synchronization.

Release sequence:

1. Merge PRs to `main` with conventional commit titles.
2. release-please opens or updates a **Release PR** (e.g.
   `chore: release 0.2.0`) with `packages/oka/CHANGELOG.md` and `VERSION`.
   [`.github/workflows/release_pr_sync_versions.yml`](https://github.com/Arenukvern/oka/blob/main/.github/workflows/release_pr_sync_versions.yml)
   derives package versions, internal dependency constraints, plugin manifests,
   and the marketplace catalog from
   that one version and commits any drift.
3. Review the Release PR, run `just check-contracts`, then merge it.
4. release-please creates the `vX.Y.Z` tag and GitHub release **with changelog
   notes**.
5. [`.github/workflows/pub_publish.yml`](https://github.com/Arenukvern/oka/blob/main/.github/workflows/pub_publish.yml)
   runs on the tag: asserts tag == `VERSION`, per-package dry-run preflight,
   then publishes all seven packages in dependency order. The package inventory
   and ordering live in the release tooling under `tool/release/`.
   Each dependency must be available on pub.dev before a dependent package
   is published. All packages share `VERSION`; web requires core `0.2.0`
   or newer. A workspace dry-run does not prove hosted consumer compatibility.
   The publish workflow checks an independent hosted consumer after the complete
   train is available. Configure pub.dev automated publishing for each package
   before the first tag-driven release.

Local preflight (does not publish):

```bash
just publish-dry-run
bash tool/ci/check_package_consumer.sh  # isolated local package consumer
```

CI also runs `test/adr0011_apk_contents_test.dart` with
`OKA_REQUIRE_REAL_ANDROID_SMOKE=true`: missing prerequisites fail that job
instead of skipping the real APK/AAB builds.

Manual fallback (when automation is blocked):

```bash
bash tool/release/sync_version.sh --version 0.2.0   # or: just sync-version
# update packages/oka/CHANGELOG.md; keep the release-please manifest
# at the last actually released version until the release is recorded
just check-contracts
git commit -am "chore: release 0.2.0" && git tag v0.2.0 && git push --tags
```

## Contract gates

Run before every merge (`just check-contracts`):

| Gate | Checks |
|---|---|
| `check_version_sync.sh` | VERSION == all package versions and internal constraints == plugin manifests == marketplace |
| `check_docs_drift.sh` | Invariants documented; fast-settings keys present; docs.json sidebar resolves |
| `check_no_personal_paths.sh` | No `/Users/<maintainer>/` paths in tracked files |
| `check_changelog_markdown.sh` | MD052 disable header kept; no bare `[bracket]` identifiers |

## Pull requests

- Keep changes minimal and focused; match existing style.
- Add/adjust tests for anything that changes packaging or pipeline behavior.
- Run `just lint && just test && just check-contracts` before pushing.
